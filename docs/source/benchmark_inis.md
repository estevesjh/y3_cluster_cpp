# Benchmark and precision-reference `.ini` files

`cosmosis-models/des_y3_cpp0d_fast.ini` and
`cosmosis-models/des_y3_cpp3d_slow_reference.ini` are not the production
pipeline ({doc}`running` covers that, `cosmosis-models/des_y3.ini`). They
exist to run *all* the des_y3 C++ backends of one kind (fixed-GL `0d`, or
adaptive Cuhre `3d`) in a single pipeline, for timing and precision
benchmarking. This page is the config contract for both, written up after
several rounds of setup failures on the `3d` file so the next person (or
agent) doesn't have to re-derive it from the C++ source. If you are
extending either file, read this first.

## The two files

| File | Backends | Cost/sample | Purpose |
|---|---|---|---|
| `des_y3_cpp0d_fast.ini` | `NumCountsSel`, `Shear1hMisSel`, `ShearPrjGl`, `Shear1h2hMax` (all fixed-GL) | ~170 ms – 2.8 s (login node) | MCMC-viable production-backend smoke test |
| `des_y3_cpp3d_slow_reference.ini` | `NumCounts3d`, `Shear1h3d`, `Shear1h2hMax3d` (adaptive Cuhre), `shear_prj_cuhre` (adaptive inner + fixed-GL outer) | ~4–225 s/module at the reduced grid below; the full 12-bin × 10-radius wall is 50–190 minutes | precision reference for the fixed-GL backends, not MCMC-viable |

Both are driven by `cosmosis-models/mock_mcmc_widePlanck_values_mis.ini`
(widePlanck fiducial + the Y3 `[miscentering]` defaults `f_mis=0.22`,
`tau_mis=0.17`) and both need `Y3_CLUSTER_CPP_DIR`, `COSMOSIS_SRC_DIR`
pointed at this checkout (see {doc}`running` for the full environment
recipe). Run from the repo root:

```bash
cosmosis cosmosis-models/des_y3_cpp0d_fast.ini
cosmosis cosmosis-models/des_y3_cpp3d_slow_reference.ini
```

Outputs land in `<basename>_output/`, gitignored, next to the `.ini`.

## Two module-wrapper contracts, two very different config rules

Every C++ module in this repo is generated by one of the macros in
`src/utils/module_macros.hh`. The `.ini` keys you must supply depend
entirely on **which wrapper** the macro instantiates — this is the
single biggest source of "BadSectionAccess" / "BadDataBlockAccess"
setup crashes.

### `CosmoSISScalarIntegrationModule<I>` (adaptive Cuhre/PAGANI modules)

Used by `NumCounts3d`, `Shear1h3d`, `Shear1h2hMax3d`, `NumCountsSel`,
`Shear1hMisSel`, and other `SCALAR_INTEGRATION` modules.
`src/utils/CosmoSISScalarIntegrationModule.hh`'s constructor reads five
keys unconditionally, with **no fallback default** — omit any one and
setup throws `BadSectionAccess`/aborts:

```ini
algorithm              = cuhre     ; or vegas, suave, divonne, pagani (GPU)
eps_rel                = 1e-4
eps_abs                = 1e-12
max_eval                = 10000000
use_cartesian_product = F         ; see the grid-vs-volumes section below
```

`eps_rel = 1e-4` is not a suggestion for `NumCounts3d`/`Shear1h3d`/
`Shear1h2hMax3d` specifically —
`src/pipelines/des_y3/number_counts/README.md` states `eps_rel=1e-3` is
**rejected** (it can undercount the lowest-richness bin) and `1e-4` is
"the accepted setting"; `shear_1h2h/README.md`'s `3d` row reports
`eps_rel=1e-4`, 51 s/sample, `3.3e-4` vs the Python reference. Don't
loosen it for these three modules.

### `CosmoSISScalarEvaluatorModule<I>` (fixed-GL / self-quadrature modules)

Used by `ShearPrjGl`, `shear_prj_cuhre`, `Shear1h2hMax`, `b_sel_marg`,
and other `SCALAR_EVALUATOR` modules (`src/utils/CosmoSISScalarEvaluatorModule.hh`).
These do their own quadrature inside `set_sample`/`evaluate`, so there
is **no** `algorithm`/`eps_rel`/`eps_abs`/`max_eval`/`use_cartesian_product`
at the wrapper level — each class reads its own science knobs, almost
always with `has_val(...) ? ... : default` fallbacks (check the specific
class in `src/models/*.hh` before assuming a key is required). Don't
copy the five integration-module keys into one of these sections; they
are silently ignored (harmless, but misleading — remove them).

## The grid/volume "wall of numbers" contract

`src/utils/make_grid_points.hh::make_grid_points_wall_of_numbers` and
`src/utils/make_integration_volumes.hh::make_integration_volumes_wall_of_numbers`
both **zip arrays 1:1** — every named axis vector must be the *same
length*, one entry per point. There is no cartesian expansion inside
these helpers (`make_grid_points_cartesian_product` exists but none of
the des_y3 3d modules call it). Check the module's own `make_grid_points`
in its header (`src/pipelines/des_y3/.../*.hh`) — it names its axes
explicitly:

- `NumCounts3d::make_grid_points` → `"bin_index"` only (one axis: the
  grid *is* the bin list, no radius).
- `Shear1h3d::make_grid_points` / `Shear1h2hMax3d::make_grid_points` →
  `"bin_index", "r_perp"` (two axes, zipped). The header comment on
  `shear1h_3d_t.hh` spells out the intended shape: *"bin_index and
  r_perp arrays of length n_bins * n_R (bin slow, R fast), with the
  volume arrays repeated per radius."* Giving `bin_index` 12 entries and
  `r_perp` 10 entries (one set of unique labels each) throws
  `"unequal length axes in make_grid_wall_of_numbers"` — you must
  pre-expand to the full `n_bins * n_R` product (or a reduced subset of
  it, see below), not list each axis's unique values once.
- Separately, `use_cartesian_product` (the *integration-module* key,
  not a grid property) controls whether the **volume** arrays
  (`lt_low`/`lt_high`/`zt_low`/`zt_high`/`lnm_low`/`lnm_high`) are
  cartesian-combined with the grid or zipped 1:1 against it. For these
  three modules the documented/validated setting is `F` — the volume
  arrays must also be the *same length as the grid* (repeat the shared
  window once per point if it doesn't actually vary).

**`lam_min`/`lam_max`/`zob_min`/`zob_max`/`sigma_z` are a different
kind of array** — a per-bin-LABEL lookup table, indexed at runtime by
the literal *value* that appears in `bin_index` (`lam_min_[b]` where
`b = bin_index[i]`), not by grid position. Keep these at the full
12-entry array (indices 0–11) even if your `bin_index` wall only visits
a subset of labels — shrinking them to match a reduced grid makes
`bin_index` values point out of bounds.

### Reducing the grid for a login-node run

The full `Shear1h3d`/`Shear1h2hMax3d` wall is 12 bins × 10 radii = 120
points at 25–95 s/point (50–190 minutes) — too slow interactively. The
file already established the right pattern for `shear_prj_cuhre`
(reduced to a 3-point angular grid, 1 λ-bin × 1 z-bin × 3 radii,
documented inline with a wall-clock note and issue #23); the same file
now reduces `Shear1h3d`/`Shear1h2hMax3d` to a 6-point wall — inner/mid/
outer radius at the two extreme (richness, redshift) corners:

```ini
bin_index = 0 0 0 11 11 11
r_perp    = 0.20000 0.83625 5.00000 0.20000 0.83625 5.00000
lt_low   = 0.5    0.5    0.5    0.5    0.5    0.5
lt_high  = 2000.0 2000.0 2000.0 2000.0 2000.0 2000.0
zt_low   = 0.05   0.05   0.05   0.05   0.05   0.05
zt_high  = 0.80   0.80   0.80   0.80   0.80   0.80
lnm_low  = 29.9336 29.9336 29.9336 29.9336 29.9336 29.9336
lnm_high = 36.7300 36.7300 36.7300 36.7300 36.7300 36.7300
```

with `lam_min`/`lam_max`/`zob_min`/`zob_max`/`sigma_z` left at their
full 12-entry lookup. `NumCounts3d` has no radius axis, so it stays at
the full 12 bins (single triple integral per bin, ~3.7 s total — cheap).
Whenever you bound a benchmark ini's coverage like this, say so in a
comment with the full-grid wall-clock cost, so a reader doesn't mistake
the reduced sample for full coverage.

## The `lt` bound is richness, not a copy of `zt`

`lt_low`/`lt_high` bound $\lambda_{\rm true}$ (richness), completely
independent of `zt_low`/`zt_high` (redshift) — an easy copy-paste bug
since both often get written near each other. `num_counts_3d_t.hh`'s
header states the requirement directly: *"the lt volume must cover the
HOD support inside the mass envelope (lt_high ~ 2000 at the Y3
fiducial)... lt_low must be strictly positive: the EMG parameter
provider is singular at lt = 0."* Use `lt_low = 0.5`, `lt_high = 2000.0`
for `NumCounts3d`/`Shear1h3d`/`Shear1h2hMax3d`; other inis in this repo
(`smoke_sel_camb.ini`, `mock_mcmc_cp_camb.ini`) use `0.5`/`800.0` for
different (fixed-GL) backends — don't assume the fast- and slow-backend
bounds are interchangeable, check the specific module's own header.

## Ini arrays that look like integers must carry a decimal point

CosmoSIS infers an ini array's element type from its literal text; an
array with no decimal point anywhere (`lambda_bin = 0 0 0`) is typed as
a vector of `int`, and any C++ read via `get_vector_double(...)` throws
`BadDataBlockAccess` on it (even though the *value* is perfectly valid
as a double). Any array a C++ model reads with `get_vector_double` —
`lambda_bin`, `bin_index`, `zo_low`, etc. — must be written with an
explicit decimal on every entry: `lambda_bin = 0.0 0.0 0.0`. This bites
most often on bin-index-like arrays because the natural way to write
them is bare integers.

## `module_label()` can be decoupled from the pipeline module name

Every `setup(DataBlock* cfg)` C-ABI entry point receives the **entire**
merged options `DataBlock`, not a view pre-scoped to the calling
module's `[pipeline] modules=` label. Each C++ class picks its own
config section by calling `cfg.view<T>(module_label(), key)`, where
`module_label()` is a **hardcoded string literal** in the class — by
convention it matches the class/`.cc`/ini-section name
(`Shear1h3d::module_label()` returns `"Shear1h3d"`), but nothing enforces
that. `y3_cluster::ShearPrjCuhre` (`src/models/sigma_prj_t.hh`) is the
one exception in this pipeline: its `module_label()` hardcodes the
lowercase `"shear_prj_cuhre"`, decoupled from the class name
`ShearPrjCuhre` and the `.so`/`.cc` file name. The ini section — and
the `[pipeline] modules=` entry, since that's what cosmosis uses to
find the section holding `file=` — **must** be `[shear_prj_cuhre]`
(all lowercase), not `[ShearPrjCuhre]`. Two other inis in this repo
(`smoke_sel_camb.ini`, `smoke_full_sel_cp_camb.ini`) already use the
correct lowercase name; a section literally named `[ShearPrjCuhre]`
loads the `.so` fine (that only needs the `file=` key to resolve) but
every `cfg.view(module_label(), ...)` call inside its constructor then
misses, and the module aborts with `BadDataBlockAccess` — the error
gives no hint that the section name itself is the problem.

## `shear_prj_cuhre` has a hidden runtime dependency on `b_sel_marg` + `bsel`

`y3_cluster::ShearPrjCuhre::set_sample` calls
`y3_cluster::sp_detail::read_bsel_vector(sample, "b_small"/"b_large")`
(`src/models/bsel_bins_t.hh`), which reads datablock section
`b_sel_marginalised` — published by the **Python** `bsel.py` module,
which itself consumes the **C++** `b_sel_marg` module's raw
`b_sel_marg_{P1,I1,J}` output plus `sel_function`'s `lambda_edges`. If
`b_sel_marg` and `bsel` are not both present in `[pipeline] modules=`
*before* `shear_prj_cuhre`, setup succeeds (their absence is invisible
at construction time) but the first `execute()` throws
`BadDataBlockAccess` deep inside `shear_prj_cuhre` — this is the
runtime-only failure a bare Python traceback doesn't localize (the
process aborts via `std::terminate`, and the visible Python traceback
only shows the `ctypes` call boundary, not the C++ frame). Diagnosing it
took a `gdb -batch -ex "catch throw" -ex run -ex bt` run (see below); the
one-line fix was restoring `b_sel_marg bsel` to the modules list ahead
of `shear_prj_cuhre`.

Required module order for any pipeline that includes `shear_prj_cuhre`,
`dsigma_prj_3d_gpu_t.cuh`, or `shear_prj_frozen_gpu_t.cuh` (the other
two `read_bsel_vector` consumers):

```
... sel_function
    b_sel_marg bsel
    ... <anything consuming b_sel_marginalised> ...
```

## Debugging an `execute()`-time `BadDataBlockAccess` with gdb

A crash during `setup()` prints which wrapper failed
(`CosmoSISScalarIntegrationModule`/`CosmoSISScalarEvaluatorModule`) but
not which key. A crash during `execute()` prints nothing but a bare
Python traceback ending at the `ctypes` call into the `.so` — the
actual C++ throw site is invisible without a debugger. To get the real
frame:

```bash
PYEXE=$(python3 -c "import sys; print(sys.executable)")
gdb -q -batch \
    -ex "catch throw" -ex "run" -ex "bt" \
    --args "$PYEXE" $(which cosmosis) cosmosis-models/<the>.ini
```

`catch throw` stops at the `__cxa_throw` call for *any* C++ exception
(not just the one that ultimately escapes uncaught), so on a pipeline
with internal try/catch-and-retry logic (like `read_bsel_vector`'s
`get_vector_double` → `ndarray` fallback) you may need `continue` once
or twice before the *fatal* throw. `bt` then shows the real call chain,
e.g. `y3_cluster::ShearPrjCuhre::set_sample` →
`y3_cluster::sp_detail::read_bsel_vector` → `get_vector_double` — which
is what actually localized both of the `shear_prj_cuhre` bugs above.

## Validated end state (2026-08-25)

Both files run cleanly end to end with `exit=0` and all integration
statuses `0` (converged):

```
$ cosmosis cosmosis-models/des_y3_cpp0d_fast.ini
...
Total pipeline time: 2.76 seconds

$ cosmosis cosmosis-models/des_y3_cpp3d_slow_reference.ini
...
NumCounts3d took: 3.659 seconds
Shear1h3d took: 3.720 seconds
Shear1h2hMax3d took: 4.201 seconds
shear_prj_cuhre took: 224.771 seconds
Total pipeline time: 2.39e+02 seconds
```

`shear1h2hmax3d`'s first two wall entries equal `shear1h3d`'s exactly
(the max model correctly falls back to the 1-halo-only value at these
points — see the `max_model_is_never_less_than_1h_only` invariant in
`test/shear1h_cross_backend.test.py`).
